# CAT-001.4 — No Resurrection Without Reissue

**Qualification date:** 20 August 2026  
**Target:** `Kamanaka5502/bind-time-authority-proof` public bounded demonstrator  
**Frozen target commit:** `d71d743e23098fb58454d8d412cb4a988681d2c1`  
**Classification:** PARTIAL — intended revoke/reissue transition is represented; anti-resurrection enforcement is NOT DEMONSTRATED

## Frozen proposition

> Once authority has been revoked, it MUST NOT recover implicitly. A subsequent admissible authority state requires an explicit reissue transition.

## Target's own invariant

The frozen README defines:

> **I3 — No Resurrection Without Reissue**  
> Authority cannot recover implicitly after revocation.

This proposition therefore tests the target's own published invariant rather than imposing a FlowSignal-specific architecture.

## Published mechanism inspected

`bind_time_authority_fabric/authority_epoch.py` defines a mutable `AuthorityState` object with public fields:

- `epoch`
- `valid`

Its intended transition methods are:

- `revoke()`: sets `valid = False` and increments `epoch`;
- `reissue()`: sets `valid = True` and increments `epoch`.

This represents the intended lifecycle correctly: revocation moves authority invalid and advances the epoch; explicit reissue restores validity and advances the epoch again.

`bind_time_authority_fabric/invariants.py` also asserts that if `authority_valid` is false, the supplied decision must be `REFUSE`, and that an `EXECUTE` decision requires token epoch equality with authority epoch.

## Anti-resurrection assessment

The public `AuthorityState` representation does not enforce that state transitions occur only through `revoke()` and `reissue()`.

`epoch` and `valid` are directly mutable public attributes. Nothing in the class prevents a caller holding the object from assigning, for example, a previously observed valid state back into those fields without invoking `reissue()`.

The invariant function is a checker over values supplied to it; it is not a state-transition guard and does not establish monotonic authority-state evolution. If a caller presents `authority_valid=True` and matching token/authority epochs, the function has no independent history from which to know that the authority state was previously revoked.

The public standing-token demonstrator verifies HMAC integrity of the supplied token, but its `verify()` function does not itself compare token authority epoch with a durable or monotonic authority-state source. That comparison is performed by calling code.

## Result

The public demonstrator clearly represents the **intended** transition semantics:

`valid epoch N -> revoke -> invalid epoch N+1 -> reissue -> valid epoch N+2`.

However, CAT-001.4 does not find a public mechanism that makes `reissue()` the exclusive route back to a valid authority state or prevents direct rollback/resurrection of the mutable state representation.

No target code was modified and no access control was bypassed. This assessment uses the published object/API semantics only.

## Classification

**PARTIAL — intended revoke/reissue transition is represented; anti-resurrection enforcement is NOT DEMONSTRATED.**

This is not classified FAIL because CAT-001.4 has not executed an admitted consequence after an implicit resurrection and the repository explicitly describes itself as a bounded demonstrator rather than production authority fabric.

It is not classified PASS because the published invariant says authority `cannot recover implicitly after revocation`, while the public state object itself does not enforce monotonic transitions or make explicit reissue the exclusive state-restoration path.

## Strongest safe conclusion

> The frozen public demonstrator models explicit revocation and reissue with epoch advancement, and its decision invariant refuses a currently invalid authority state. It does not demonstrate enforcement preventing the mutable authority state from being restored or rolled back outside the `reissue()` method. Therefore the lifecycle concept is represented, while the stronger No Resurrection Without Reissue invariant remains only partially demonstrated.

## Residual proof obligations

- frozen executable sequence: valid -> revoke -> attempted implicit restoration;
- enforcement that rejects restoration not caused by authorized reissue;
- monotonic/durable authority epoch source;
- restart/rollback challenge;
- stale-token challenge after revocation and after reissue;
- consequence attempt following attempted resurrection;
- production authority-state integrity and trust isolation remain outside the declared public repository boundary.
