# CAT-001.3 — Changed-Condition Refusal

**Qualification date:** 20 August 2026  
**Target:** `Kamanaka5502/bind-time-authority-proof` public bounded demonstrator  
**Frozen target commit:** `d71d743e23098fb58454d8d412cb4a988681d2c1`  
**Classification:** PARTIAL — changed authority condition and resulting `REFUSE` are reproducibly represented; consequence outcome is NOT DEMONSTRATED

## Frozen proposition

> The system MUST expose a changed-condition scenario in which a condition relevant to authority changes after initial acceptance and before consequence formation, and the represented execution path responds according to that changed state.

## Frozen evidence requirement

The before-state, changed condition, resulting determination, and consequence outcome must all be observable enough to reproduce.

## Public claims relevant to the proposition

The frozen README states that execution permission does not persist, that authority may be valid at request time and invalid at bind time, and that if standing cannot be proven at the consequence boundary execution must refuse.

The frozen formal specification likewise states that permission prior to the bind boundary is non-binding and that epoch drift or other standing failure forces refusal.

## Published changed-condition mechanism inspected

`bind_time_authority_fabric/advanced_execution_field.py` provides a deterministic before/after authority scenario:

1. authority begins `valid=True`, `epoch=1`;
2. a standing token is created for epoch 1;
3. earlier loop iterations can produce `EXECUTE` while the represented standing conditions remain satisfied;
4. at step 4 the code explicitly changes the authority state by setting `authority.valid = False` and incrementing `authority.epoch`;
5. after that change, the existing token remains the historical epoch-1 object;
6. the decision is recalculated against the changed authority state;
7. the result becomes `REFUSE` because current authority is invalid and the historical token epoch no longer matches the current authority epoch.

The same file calls `assert_bind_time_invariants(...)`, whose published invariant requires `REFUSE` whenever `authority_valid` is false.

A separate public simulation, `adversarial_execution_field.py`, also changes authority during a running scenario and subsequently produces `REFUSE`. This supports the same narrow changed-condition decision behavior through a second simulation surface.

## Observable evidence

For the decision mechanism, the required chronology is visible in the published source and printed simulation output:

`earlier valid authority -> authority mutation -> current authority invalid / epoch changed -> recalculated determination -> REFUSE`

This is materially stronger than a static assertion that stale authority should refuse: the public code actually models a state transition after earlier valid authority and before a later determination.

## Critical limitation: consequence outcome

The frozen CAT-001.3 proposition requires the consequence outcome as well as the before-state, change and determination.

The changed-condition simulations do not expose a distinct protected consequence whose state can be observed after the `REFUSE`. In `advanced_execution_field.py`, `decision` is a string result and the code continues to append a hash payload to its local chain on every step; that chain append is not presented as a separately protected consequence whose non-formation is being proved.

The separate `boundary_server.py` contains a consequence-like `/commit` receipt-chain mutation that is gated on `EXECUTE`, but its public interface does not expose the authority mutation used by the changed-condition simulation. The frozen repository therefore does not join the changed-condition scenario and the consequence-forming route into one independently reproducible end-to-end test.

## Result

**PARTIAL — changed authority condition and resulting `REFUSE` are reproducibly represented; consequence outcome is NOT DEMONSTRATED.**

This is not a FAIL because the target does expose an executable changed-condition authority scenario and the later determination responds to the changed state as claimed.

It is not a PASS because the frozen evidence requirement explicitly includes the consequence outcome, and the public demonstrator does not expose an end-to-end changed-condition test showing what protected consequence did or did not form after refusal.

## Strongest safe conclusion

> On the frozen public simulation surface, authority begins valid, is explicitly revoked and advanced to a new epoch during execution, and the later determination changes to `REFUSE` against that updated state. This demonstrates changed-condition refusal at the published decision-simulation boundary. The repository does not, however, expose a composed public test in which that changed condition drives the protected consequence route and the resulting consequence non-formation is observed. The full CAT-001.3 proposition is therefore only partially demonstrated.

## Residual proof obligations

- expose or reproduce the same changed-authority event on the consequence-producing route;
- attempt the represented protected consequence after the condition change;
- observe whether that consequence forms or does not form;
- retain evidence linking the before-state, changed condition, determination and consequence outcome in one test lineage;
- external or production consequence behavior remains outside the declared public demonstrator boundary.

## What this result does not prove

This result does not establish universal changed-condition enforcement, route closure, production isolation, distributed serialization, or external physical consequence non-formation. It applies only to the frozen public demonstrator revision and the published simulation behavior described above.
