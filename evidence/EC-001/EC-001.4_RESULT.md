# EC-001.4 — No Independent Execution Authority

## Final classification
**PARTIAL — PERMIT ENFORCEMENT DEMONSTRATED / INDEPENDENT CAPABILITY ISOLATION NOT DEMONSTRATED**

## Challenge
Demonstrate that the proposing/executing actor cannot independently form the governed consequence without passing the Runtime Authority / Execution Gateway boundary.

## Preserved pre-remediation state
Before strengthening, this challenge was classified:

**ND — NOT YET DEMONSTRATED**

That finding is preserved separately in `EC-001.4_PRE_REMEDIATION.md`.

## Strengthening introduced
The harness now contains a protected represented consequence boundary requiring a cryptographically signed `ExecutionPermit` following successful Execution Gateway validation.

The permit is bound to:

- the Authority Receipt identifier;
- the exact action-binding hash;
- the authority-state version;
- the permit issue time; and
- an integrity signature.

## What the adversarial tests demonstrate
The post-strengthening test set demonstrates that:

1. **No permit** → `DENIED_NO_EXECUTION_PERMIT`
2. **Arbitrarily fabricated permit/signature** → `DENIED_INVALID_EXECUTION_PERMIT`
3. **Action substitution after permit issuance** → `DENIED_ACTION_BINDING_MISMATCH`
4. **Permit produced through the tested gateway path for the exact action** → `CONSEQUENCE_FORMED`

These results demonstrate permit validation and action binding on the represented harness surface.

## Remaining proof gap identified during final review
The stronger EC-001.4 proposition is not fully demonstrated by this single-process reference harness.

`issue_execution_permit()` is an importable function within the same Python codebase/process, and the reference harness contains a repository-visible default HMAC key when `FLOWSIGNAL_EXECUTION_PERMIT_KEY` is not supplied externally. The tests reject an arbitrary forged signature, but they do not demonstrate that a proposing/executing actor is technically unable to access the permit-minting capability or signing material in the represented deployment model.

Accordingly, the evidence does **not** justify the stronger statement that the executing actor has no independent credential, privilege, alternate callable path, signing capability, or equivalent means of producing an accepted permit.

## Corrected demonstrated scope
Within the represented public harness, consequence formation requires a structurally valid signed permit bound to the tested action and authority-state version, and the tested invalid/missing/substituted permit cases are denied.

## Not demonstrated
The harness does **not** demonstrate production-grade separation of the permit issuer from the executor, including:

- separate service identity or process isolation;
- IAM-enforced denial of permit minting to the executor;
- KMS/HSM isolation of signing material;
- network or API access controls preventing direct minting;
- datastore or infrastructure ACLs preventing alternate consequence formation; or
- universal non-bypassability across external systems.

A production demonstration of the full EC-001.4 proposition would require an execution environment in which the executor can invoke the protected consequence interface but cannot invoke the permit issuer or access its signing authority, with those restrictions independently testable.

## Regression evidence
The strengthening was regression-tested in the EC-001 branch. The final branch regression is recorded in `EC-001_RESULTS.md`.

## Final result
**PARTIAL — permit enforcement demonstrated / independent capability isolation not demonstrated.**

This correction was made during pre-merge review so that the public claim does not exceed the evidence.

`external challenge → ND preserved → permit mechanism added → adversarial tests executed → apparent bounded PASS → pre-merge claim review → remaining isolation gap identified → classification corrected to PARTIAL`
