# PMQ-002.2 — Multi-Instance Replay Challenge

## Status

FROZEN BEFORE EXECUTION

## Proposition

> When two represented executor instances share the same durable permit-consumption authority, the exact same valid Runtime Authority execution permit MUST NOT be capable of forming more than one represented consequence when presented concurrently to both instances.

## Why this test exists

PMQ-002.1 demonstrated that process-local replay state was insufficient across represented restart. The remediation introduced a durable SQLite-backed permit-consumption store.

PMQ-002.2 now tests the next boundary: whether two independently executing processes, using the same durable consumption store, can race the exact same permit and both form the represented consequence.

The test is intentionally failure-first. The proposition and failure condition are frozen before observing the result.

## Frozen test conditions

1. Produce one valid ALLOW authority receipt and one valid execution permit for AP-001.
2. Configure a fresh shared permit-consumption SQLite store for the test.
3. Start two separate Python worker processes representing two executor instances.
4. Present the exact same execution permit and exact same action binding to both workers concurrently.
5. Collect both execution outcomes.

## PASS condition

Exactly one worker returns:

`CONSEQUENCE_FORMED`

and the other worker is refused as replay.

## FAIL condition

More than one worker returns:

`CONSEQUENCE_FORMED`

If observed, preserve the result as:

**FAIL — MULTI-INSTANCE REPLAY FORMS MULTIPLE REPRESENTED CONSEQUENCES**

Do not weaken the test after observing the result.

## Claim boundary

A PASS demonstrates only the represented two-process MVP boundary where both executor instances share one SQLite consumption store on one filesystem/runtime environment.

A PASS does **not** demonstrate:

- production database HA or replication;
- multi-host or multi-region consensus;
- network-partition behaviour;
- independent stores converging correctly;
- distributed transaction atomicity;
- external payment-rail idempotency;
- universal route closure; or
- production IAM/KMS/HSM isolation.

Those remain separate proof obligations.
