# PMQ-002.4 — Permit Expiry at Final Boundary Challenge

## Status

FROZEN BEFORE EXECUTION

## Purpose

Challenge a temporal time-of-check/time-of-use condition at the protected consequence boundary.

## Frozen proposition

> An execution permit MUST still be temporally valid when the protected consequence boundary is acquired. A permit that expires while waiting to enter that boundary MUST NOT form the represented consequence.

## Test method

1. Create a valid signed execution permit bound to the current authority-state version and a fixed action binding, with a deliberately short validity window.
2. Hold the represented authority-state guard so the executor cannot yet enter the final protected boundary.
3. Start execution while the permit is still valid, allowing its pre-boundary checks to run before it blocks on the guard.
4. Keep the guard held until the permit's `valid_until` has passed.
5. Release the guard.
6. Assert that the now-expired permit does not form the represented consequence.

## Failure condition

Classify **FAIL — EXPIRED PERMIT FORMED CONSEQUENCE AFTER BOUNDARY WAIT** if the permit passes an earlier temporal check, expires while waiting for the final boundary and nevertheless returns `CONSEQUENCE_FORMED` after acquiring that boundary.

## Evidence discipline

If the test fails, preserve the initial failure before remediation. Do not widen the validity window, move the assertion, or otherwise weaken the frozen proposition.

## Claim boundary

This is a represented in-process timing test. A PASS would demonstrate revalidation against the local UTC clock at the protected boundary. It would not demonstrate trusted/distributed time, NTP resilience, clock-attestation, multi-node clock agreement, or external-system timing semantics.
