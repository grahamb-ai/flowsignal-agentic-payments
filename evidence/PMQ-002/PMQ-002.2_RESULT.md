# PMQ-002.2 — Multi-Instance Replay Result

## Frozen proposition

> When two represented executor instances share the same durable permit-consumption authority, the exact same valid Runtime Authority execution permit MUST NOT be capable of forming more than one represented consequence when presented concurrently to both instances.

## Execution lineage

### Initial run

GitHub Actions run `32160449500`

`1 failed, 43 passed`

Both workers returned `DENIED_AUTHORITY_STATE_STALE` because independently spawned processes initialized their in-memory authority state at version `1` while the parent test process had already advanced the state version.

Classification:

**NOT EVALUATED — MULTI-INSTANCE REPLAY PROPOSITION NOT REACHED**

The fixture was corrected only to align each worker's authority-state version to the already-issued permit. The frozen permit, binding, two-process race and replay proposition were unchanged.

### Corrected-fixture run

GitHub Actions run `32160570769`

`1 failed, 43 passed`

One worker reached the durable permit-consumption store while the other failed during concurrent SQLite initialization with:

`sqlite3.OperationalError: database is locked`

Replay proposition classification:

**NOT EVALUATED — MULTI-INSTANCE REPLAY PROPOSITION NOT CONCLUSIVELY REACHED**

Additional defect classification:

**FAIL — CONCURRENT DURABLE-STORE INITIALIZATION IS NOT ROBUST UNDER THE TESTED TWO-PROCESS RACE**

The failure was preserved before remediation.

### Remediation

The durable permit-consumption store was strengthened with bounded SQLite busy/lock retry behaviour during shared-store initialization while retaining atomic `INSERT OR IGNORE` permit consumption.

The replay proposition and two-process concurrency semantics were not weakened.

### Rerun after remediation

GitHub Actions run `32160709132`

`44 passed in 0.92s`

The same exact execution permit was raced across two independent Python executor processes sharing one durable SQLite consumption store.

Exactly one represented consequence formed; the competing permit use did not form a second consequence.

## Final classification

**PASS — REPRESENTED TWO-PROCESS SHARED-STORE REPLAY BLOCKED**

## Demonstrated scope

Within the represented MVP test boundary, two independent Python executor processes sharing the same SQLite permit-consumption store did not form more than one represented consequence from the same valid execution permit under the tested concurrent race.

The test also demonstrates that the remediated store initialization tolerated the tested two-process contention case.

## Residual limitations

This result does **not** demonstrate:

- production database HA or replication;
- separate-host or multi-region consensus;
- behaviour during network partitions;
- correctness where executor instances use independent/non-shared stores;
- distributed transaction atomicity across authority state, permit consumption and external consequence systems;
- external payment-rail idempotency;
- universal route closure; or
- production IAM/KMS/HSM isolation.

Those remain separate proof obligations.
