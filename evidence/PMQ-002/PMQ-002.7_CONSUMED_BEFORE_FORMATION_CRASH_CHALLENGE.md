# PMQ-002.7 — Consumed-Before-Formation Crash Challenge

## Frozen proposition

> If a valid execution permit has been durably consumed but the executor fails before the represented consequence forms, recovery MUST preserve an explicit recoverable state showing that the consequence did not form; the system MUST NOT silently collapse that state into an indistinguishable consumed-permit replay denial.

## Attack

1. Issue a valid execution permit for the current authority state and exact action binding.
2. Enter the represented protected consequence path.
3. Allow durable one-time permit consumption to complete.
4. Inject executor failure immediately before the represented consequence forms.
5. Recover using the same durable stores.
6. Determine whether the system can distinguish:
   - permit consumed + consequence formed; from
   - permit consumed + consequence did not form.

## Failure condition

The proposition fails if, after the injected failure, the only durable fact is that the permit has been consumed and recovery cannot establish that the represented consequence did not form.

A subsequent `DENIED_EXECUTION_PERMIT_REPLAY` is not sufficient evidence of prior consequence formation.

## Evidence discipline

This proposition is frozen before remediation. If the current architecture cannot recover the outcome of the consumed-before-formation crash window, preserve the failure before changing implementation.

## Claim boundary

This is a represented reference-MVP crash/recovery challenge. It does not establish production host/process crash durability, external payment-rail reconciliation, distributed transactions, infrastructure HA, external exactly-once execution or physical consequence status.
