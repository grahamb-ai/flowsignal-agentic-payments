# PMQ-002.5 — Authority-State Rollback / Stale-State Resurrection

## Frozen proposition

> Once the represented authority state has advanced to a newer version, an older authority-state version MUST NOT be restorable through the supported authority-store interface in a way that makes a permit bound to that older version current again and able to form the represented protected consequence.

## Why this matters

Version checking only prevents stale execution while the authority-state version remains monotonic. If an older state can be restored as current, a previously stale permit could potentially become apparently current again.

PMQ-002.5 therefore challenges the monotonicity of the represented authority-state mechanism rather than merely checking that stale permits are rejected under normal forward-only state changes.

## Frozen test method

1. Record authority-state version N.
2. Mint a valid execution permit bound to N.
3. Advance the authority state to N+1.
4. Confirm the permit bound to N is stale and cannot form the represented consequence.
5. Attempt to restore N using the supported authority-store mutation surface.
6. If rollback is accepted, retry the previously stale permit against the represented protected consequence.
7. PASS only if the supported authority-store interface prevents stale-state resurrection from making the old permit executable again.

## Scope

The proposition is intentionally bounded to the supported represented authority-store interface.

It does **not** claim protection against arbitrary process-memory mutation, direct source modification, database/storage restoration outside the application interface, administrative compromise, replica rollback, disaster-recovery restoration, or production IAM/storage compromise.

Those remain separate proof obligations.

## Evidence discipline

The proposition is frozen before the executable challenge is introduced. Any initial failure will be preserved before remediation, and the proposition will not be weakened after execution.
