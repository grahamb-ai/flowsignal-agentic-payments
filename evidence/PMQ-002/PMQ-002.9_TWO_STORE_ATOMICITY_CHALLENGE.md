# PMQ-002.9 — Two-Store Atomicity Crash Challenge

## Frozen proposition

> Durable permit consumption and creation of the initial represented consequence-outcome state MUST NOT be separable by a crash window that leaves the permit consumed with no recoverable execution outcome.

## Attack

1. Issue a valid execution permit for the current authority state and exact action binding.
2. Execute in a spawned child process using durable permit-consumption and consequence-outcome stores shared with recovery.
3. Allow durable permit consumption to commit.
4. Terminate the child process immediately when the executor attempts to persist its first consequence-outcome state, before that outcome write can commit.
5. Restart/recover against the same durable stores.
6. Determine whether durable recovery can establish an explicit execution state rather than finding only a consumed permit.

## Failure condition

The proposition fails if permit consumption is durably committed while no durable execution/outcome state exists for the same permit/action binding after the injected crash.

A subsequent replay denial is not sufficient. It proves at-most-once permit consumption, not whether the represented consequence formed or remained unresolved.

## Evidence discipline

This proposition is frozen before runtime remediation. The test intentionally targets the exact gap left explicit by PMQ-002.8: permit consumption and initial unresolved-outcome creation currently occur in separate durable operations and separate SQLite stores.

If the current architecture fails, preserve the failure before changing the mechanism. The test proposition must not be weakened after observation.

## Claim boundary

This is a represented reference-MVP crash/atomicity challenge. It does not establish production distributed transactions, database HA, filesystem/fsync guarantees, host power-loss behavior, cross-service consensus, external payment-rail idempotency, universal route closure or physical consequence status.
