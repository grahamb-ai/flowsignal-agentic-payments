# PMQ-002.5 — Initial Failure

## Frozen proposition

> Once authority state version N has been superseded by a later committed version, the represented authority-state mechanism MUST NOT permit the current state to move backwards to N such that an execution permit bound to N can regain standing and form the represented protected consequence.

## Initial execution

GitHub Actions run: `32161900271`

Integrated result:

**1 failed / 47 passed**

## Classification

**FAIL — SUPERSEDED AUTHORITY STATE RESURRECTED**

## Observed failure

The reference authority store represented current authority standing with the mutable module-level integer `_AUTHORITY_STATE_VERSION`.

After advancing from version N to N+1, the challenge directly restored that reachable state value to N. `get_authority_state_version()` then reported the superseded version as current.

The test stopped at that first falsification point. This is sufficient to demonstrate that the represented authority-state mechanism did not itself enforce monotonicity against rollback of its reachable state representation.

## Why it matters

A permit bound to a superseded state is denied only because its recorded version differs from the authority store's current version. If the current state can be rolled backwards, stale standing can potentially be resurrected.

## Scope

This is a failure of the represented reference-harness authority-state mechanism. It is not evidence about production database rollback protection, infrastructure administrator compromise, distributed consensus or external IAM state.

The failure is preserved before remediation.
